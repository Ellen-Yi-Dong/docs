This guide covers how to adopt Kessel RBAC in an application that is **not currently using RBAC v1**. If your application is already using RBAC v1, see the [Migrate from RBAC v1 to v2](/docs/building-with-kessel/how-to/migrate-from-rbac-v1-to-v2/) guide instead.

Adopting Kessel RBAC means making Kessel the **single source of truth** for authorization decisions in your application. Rather than implementing permission logic locally, your application delegates all access checks to Kessel via `Check` and `CheckForUpdate` calls.

<Aside type="caution">
  Do not query role bindings to make authorization decisions in your application code. Use Kessel's `Check` and `CheckForUpdate` APIs — they evaluate the full authorization graph including group membership, role bindings, permission inheritance, and workspace hierarchy. See [Protect an Endpoint](/docs/building-with-kessel/how-to/protect-endpoint/) for implementation examples.
</Aside>

## Assess your starting point

Before you begin, identify where your application falls:

**Applications with existing grouping abstractions** — Your application already organizes resources into groups, folders, teams, projects, or similar containers. These map naturally to Kessel workspaces. Examples:
- Inventory groups or host collections
- Project or team boundaries
- Folder hierarchies or tenant partitions

**Applications with no existing authorization model** — Your application either has no access control, uses simple org-wide checks (e.g., "is the user in this org?"), or relies on hardcoded role logic. All resources are effectively accessible to anyone in the organization.

The sections below describe migration patterns for each case. Most applications use a combination — some resource types may have grouping while others are org-wide.

## Applications with existing grouping abstractions

If your application already groups resources (folders, teams, projects, host groups), you can map those groups to Kessel workspaces. This gives you hierarchical, inheritable permissions without reimplementing authorization logic.

### Map groups to workspaces

Identify the grouping concept in your application and decide how it maps to the workspace hierarchy:

| Your application's concept | Kessel mapping | Notes |
|---|---|---|
| Top-level container (all resources) | Root workspace | Automatically created per tenant |
| Primary grouping (projects, teams) | Standard workspaces under Default | Create one workspace per group |
| Sub-groups or nested folders | Nested standard workspaces | Permissions inherit downward through the hierarchy |
| Ungrouped or unclassified resources | Default workspace | Resources not yet assigned to a specific group |

<Aside type="tip">
  Workspace IDs for Root and Default workspaces are immutable per tenant. Cache them aggressively. See the [Migration Pattern Reference](/docs/building-with-kessel/reference/migration-pattern-reference/#caching) for caching guidance.
</Aside>

### Decide the authorization pattern per resource type

For each resource type in your application, choose a migration pattern based on whether the resource is already workspace-aware:

- **Resource already mapped to a group** — Assign the resource to the corresponding workspace via `workspace_id`. Use Pattern 1 (Native) or Pattern 2 (Native workspace-level list) depending on cardinality. See the [Migration Pattern Reference](/docs/building-with-kessel/reference/migration-pattern-reference/) for the decision tree.

- **Resource not yet mapped but could be** — Use Pattern 3 (Default workspace). Assign all resources to the Default workspace for now. This preserves org-wide behavior while making the resource compatible with workspace-scoped authorization for a future migration.

- **Org-wide settings that apply to groups** — Use Pattern 4 (Root workspace) for settings that could eventually be scoped to workspaces. Use Pattern 5 (Organization-level) for settings that will always be org-wide.

### Migrate resource-group assignments

When your application creates or updates resources, set `workspace_id` to reflect the group the resource belongs to. For existing data, run a backfill to populate `workspace_id` based on the current grouping:

<Steps>
1. Add a `workspace_id` column to your resource tables (if not already present).
2. Create workspaces in Kessel that correspond to your existing groups by calling the RBAC workspace API.
3. Backfill `workspace_id` on existing resources by mapping each resource's current group to the corresponding workspace.
4. Update resource creation and update paths to set `workspace_id` when a resource is assigned to a group.
</Steps>

<Aside type="note">
  If your existing groups have a hierarchy (e.g., nested folders), model that hierarchy as parent-child workspace relationships. Permissions granted on a parent workspace automatically apply to child workspaces.
</Aside>

### Replace group-based authorization checks

Where your application currently checks "does this user have access to this group?", replace that logic with a Kessel `Check` call against the corresponding workspace:

**Before (application-level group check):**
```
if user_has_access_to_group(user, resource.group_id):
    allow()
```

**After (Kessel authorization check):**
```
result = kessel_client.check(
    resource=workspace(resource.workspace_id),
    permission="myapp_resource_view",
    subject=principal(user.id)
)
if result == ALLOWED:
    allow()
```

For listing resources across groups, use `StreamedListObjects` to get the workspace IDs the user can access, then filter your database query. See [Protect a List Endpoint](/docs/building-with-kessel/how-to/protect-list/) for detailed examples.

## Applications with no existing authorization model

If your application has no authorization model — or uses simple org-wide checks — start with the Default workspace pattern. This is the lowest-effort path to adopting Kessel RBAC while maintaining current behavior.

### Start with the Default workspace

The Default workspace represents "all resources in this organization that aren't explicitly placed elsewhere." By checking permissions against the Default workspace, your application gets org-wide authorization that matches the current behavior:

<Steps>
1. Look up the Default workspace ID for the tenant using `GET /api/rbac/v2/workspaces/?type=default&with_ancestry=true`. The `with_ancestry=true` parameter bypasses permission validation on the request. Cache this value — it never changes for a given tenant.
2. For each protected endpoint, call `Check` or `CheckForUpdate` with the Default workspace as the resource.
3. Define your permissions in a `.ksl` file and submit them to the [rbac-config](https://github.com/project-kessel/rbac-config) repository.
4. Assign your permissions to appropriate roles (application-specific and RHEL persona-based roles).
</Steps>

This approach gives you:
- Centralized authorization through Kessel (no local permission logic)
- Compatibility with the workspace model for future workspace-scoped authorization
- Wildcard permission evaluation handled server-side by Kessel

<Aside type="note">
  For org-wide settings that will never be workspace-scoped (authentication policies, user management), use Pattern 5 (Organization-level) and check against the tenant resource instead. See the [Migration Pattern Reference](/docs/building-with-kessel/reference/migration-pattern-reference/#pattern-5-organization-level-non-asset-centric-settings).
</Aside>

### Plan for future workspace adoption

Even if you start with the Default workspace for everything, design your permission schema with future workspace support in mind:

- **Name permissions clearly** — Use the `application:resource_type:operation` format so permissions can be scoped to workspaces later without renaming.
- **Add a `workspace_id` column early** — Even if every resource points to the Default workspace initially, having the column makes future migration straightforward.
- **Use role bindings, not direct grants** — All access must go through role bindings on workspaces or tenants. This is how Kessel's authorization graph works; there is no mechanism for granting permissions directly on individual resources.

For guidance on structuring your permission schema, see [Design Permissions Schema](/docs/building-with-kessel/how-to/design-permissions/).

## Dual-running strategies

During migration, you may need to run both your existing authorization logic and Kessel in parallel. This section covers strategies for a safe, incremental transition.

### Feature flag gating

Use a feature flag to control whether Kessel authorization is active. This lets you deploy the integration code and enable it independently:

```
KESSEL_ENABLED=false  # Toggle Kessel authorization on/off
```

When `KESSEL_ENABLED` is `false`, your application uses its existing authorization path. When `true`, it calls Kessel. This flag should be the **only** difference between the two paths — no other behavioral changes should be tied to it.

<Aside type="caution">
  When `KESSEL_ENABLED` is `false`, the application must fall back cleanly to existing authorization with no side effects. Toggling should not require redeployment if possible — use a runtime feature flag system or environment variable reload.
</Aside>

### Shadow mode (log-only comparison)

Before switching authorization to Kessel, run both systems in parallel and compare results without affecting users:

<Steps>
1. **Call both** — For each authorization check, call your existing logic **and** Kessel's `Check` API.
2. **Use the old result** — The existing authorization result controls access. Kessel's result is logged but not enforced.
3. **Log discrepancies** — When the two results differ, log the details: user, permission, resource, and which system allowed or denied. These discrepancies indicate either a misconfigured permission schema or an intentional behavioral change.
4. **Investigate mismatches** — Resolve discrepancies before switching to Kessel-only mode. Common causes:
   - Missing permissions in the KSL schema
   - Workspace assignment mismatches (resource in wrong workspace)
   - Wildcard permission handling differences (Kessel evaluates server-side; your old system may have inconsistent client-side logic)
   - Role binding scope mismatches (see the [Compatibility Constraint](/docs/building-with-kessel/reference/migration-pattern-reference/#the-compatibility-constraint))
</Steps>

### Incremental rollout

Roll out Kessel authorization gradually rather than all at once:

**By endpoint** — Enable Kessel for low-risk read endpoints first, then write endpoints, then sensitive operations.

**By tenant** — Use a per-tenant feature flag to enable Kessel for specific organizations. Start with internal or test tenants, expand to a small percentage of production tenants, then roll out broadly. The insights-rbac service uses per-org Unleash feature flags for this purpose.

**By resource type** — If your application manages multiple resource types, migrate them independently. One resource type can use Kessel while others remain on the old system.

<Aside type="tip">
  Per-tenant rollout is the safest strategy for production migrations. It limits blast radius and lets you validate behavior with real data before expanding.
</Aside>

### Cutover and rollback

Once shadow mode shows consistent results across a representative set of tenants:

<Steps>
1. **Switch the feature flag** — Set `KESSEL_ENABLED=true` for the target tenants. Kessel results now control access.
2. **Keep the old path available** — Do not remove your existing authorization code immediately. Leave the feature flag in place so you can revert if issues arise.
3. **Monitor** — Watch for increased 403 responses, latency changes, or user-reported access issues. Kessel authorization checks typically complete in 10-50ms.
4. **Remove the old path** — After a stabilization period with no issues, remove the legacy authorization code and the feature flag.
</Steps>

<Aside type="caution" title="One-way activation">
  If your application uses the insights-rbac dual-write pipeline, be aware that tenant activation for v2 writes is **permanent** — once a tenant is switched to v2, v1 writes are blocked and cannot be re-enabled. Plan your rollout accordingly and ensure Kessel authorization is validated before activating v2 writes for a tenant.
</Aside>

## Which permission extension to use

KSL provides two extensions for registering permissions. Which one you use depends on whether your application has existing RBAC v1 permissions that need backward-compatible wildcard support.

**`@rbac.add_unified_permission`** — Use this for **new permissions** or applications that have **no existing RBAC v1 permissions**. This is the simpler option and the recommended default for applications adopting Kessel RBAC for the first time.

```ksl
version 0.2
namespace myservice

import rbac

@rbac.add_unified_permission(app:'myservice', resource:'integration', verb:'view');
@rbac.add_unified_permission(app:'myservice', resource:'integration', verb:'edit');
```

This creates permission names like `myservice_integration_view` and `myservice_integration_edit` that can be used in `Check` calls.

**`@rbac.add_v1_based_permission`** — Use this when your application has **existing RBAC v1 permissions** with wildcard usage (e.g., `myapp:*:read`). This extension generates the permission plus all wildcard permutations (`_all_` variants) so that existing v1 wildcard grants continue to work after migration.

```ksl
version 0.1
namespace myservice

import rbac

@rbac.add_v1_based_permission(app:'myservice', resource:'integration', verb:'read', v2_perm:'myservice_integration_view');
@rbac.add_v1_based_permission(app:'myservice', resource:'integration', verb:'write', v2_perm:'myservice_integration_edit');
```

<Aside type="note">
  `@rbac.add_v1_based_permission` requires an explicit `v2_perm` parameter for the compound permission name because it also generates the v1-compatible wildcard variants. The naming convention maps `read` to `view` and `write` to `edit` to avoid collisions with v1 permission names. See the [v1 to v2 migration guide](/docs/building-with-kessel/how-to/migrate-from-rbac-v1-to-v2/#model-the-permissions) for full details on wildcard handling.
</Aside>

For a working example of `@rbac.add_unified_permission` in context, see [Protect an Endpoint](/docs/building-with-kessel/how-to/protect-endpoint/#define-your-service-permissions).

## Migration checklist

Use this checklist to track your migration progress:

### Preparation

- [ ] Identify all resource types in your application and their current authorization model
- [ ] For each resource type, choose a [migration pattern](/docs/building-with-kessel/reference/migration-pattern-reference/) (Native, Default workspace, Root workspace, or Organization-level)
- [ ] Map existing grouping concepts (if any) to Kessel workspaces
- [ ] Determine which endpoints need `Check` vs `CheckForUpdate` (use `CheckForUpdate` for writes and sensitive reads)

### Permission schema

- [ ] Write `.ksl` permission definitions — choose the right extension for your situation (see [which extension to use](#which-permission-extension-to-use) below)
- [ ] Use `@rbac.add_contingent_permission()` for host-centric permissions that require both app-specific and inventory permissions
- [ ] Submit `.ksl` files to the [rbac-config](https://github.com/project-kessel/rbac-config) repository (stage first, then prod)
- [ ] Assign permissions to appropriate roles — both application-specific roles and [RHEL persona-based roles](/docs/building-with-kessel/reference/migration-pattern-reference/#role-definitions) (Viewer, Operator, Administrator)

### Implementation

- [ ] Add the Kessel client SDK as a dependency ([Go](https://github.com/project-kessel/kessel-sdk-go), [Python](https://github.com/project-kessel/kessel-sdk-py), [Java](https://github.com/project-kessel/kessel-sdk-java), [Node](https://github.com/project-kessel/kessel-sdk-node), [Ruby](https://github.com/project-kessel/kessel-sdk-ruby))
- [ ] Add configuration for Kessel endpoints (`INVENTORY_API_SERVER`, `RELATION_API_SERVER`, auth credentials)
- [ ] Add a `KESSEL_ENABLED` feature flag
- [ ] Implement authorization middleware using `Check` / `CheckForUpdate` — see [Protect an Endpoint](/docs/building-with-kessel/how-to/protect-endpoint/)
- [ ] For list endpoints, implement workspace-based filtering using `StreamedListObjects` — see [Protect a List Endpoint](/docs/building-with-kessel/how-to/protect-list/)
- [ ] Handle both user principals (`identity.User.UserId`) and service account principals (`identity.ServiceAccount.UserId`)
- [ ] Implement fail-closed error handling — Kessel errors (connection failures, timeouts) must result in denial, not silent allow
- [ ] If using Default or Root workspace patterns, look up workspace IDs using the service's own OAuth token (not `x-rh-identity`) with the `x-rh-rbac-org-id` header

For detailed instructions on configuring Kessel client endpoints, authentication credentials, and Clowder service discovery, see the [configuration section of the RBAC v1 to v2 migration guide](/docs/building-with-kessel/how-to/migrate-from-rbac-v1-to-v2/#add-configuration-options-for-the-kessel-client) and [Configure Authentication](/docs/building-with-kessel/how-to/configure-authentication/).

### Testing

- [ ] Write unit tests with a mock Kessel gRPC client covering: allowed, denied, error, and both principal types
- [ ] If dual-running, verify parity between old and new authorization for equivalent permissions
- [ ] Validate in an ephemeral environment with Kessel deployed
- [ ] Test with `KESSEL_ENABLED=false` to confirm clean fallback to existing authorization

### Rollout

- [ ] Deploy with `KESSEL_ENABLED=false`
- [ ] Enable shadow mode (if using dual-running) and monitor for discrepancies
- [ ] Enable for internal/test tenants first
- [ ] Expand to production tenants incrementally
- [ ] Monitor for authorization regressions (unexpected 403s, latency changes)
- [ ] After stabilization, remove the legacy authorization path and feature flag
